# Dashboard / profile view — design

**Date:** 2026-07-24 · **Target:** 1.5.0 (OTA-able on runtime 1.4.0, see §7)

## 1. Overview and goals

A Strava-like, clean and minimalist dashboard summarizing the user's recorded
activity: a period graph (past 7 days / 3 months / 1 year) of distance, time
and D+ with a scrubbable readout, and a month calendar where every day with an
activity carries its category icon and taps through to the trail. Everything is
computed from the already-persisted `TrackSummary[]` in `useLibraryStore` — no
new persistence, no network, works fully offline like the rest of the app.

## 2. Where it lives

**Decision: a 4th tab.** `app/(tabs)/dashboard.tsx` rendering
`src/features/dashboard/DashboardScreen.tsx`, registered in
`app/(tabs)/_layout.tsx` between Library and Settings:

```tsx
<Tabs.Screen name="dashboard" options={{ title: 'Dashboard', tabBarIcon: icon('chart-timeline-variant') }} />
```

Weighed against a Library header entry (`Appbar.Action` on LibraryScreen):

- The header entry keeps the tab bar at three items but buries a headline
  feature two taps deep behind an icon-only affordance; discoverability is the
  whole point of a profile view.
- Strava's own information architecture puts "You" in the tab bar; users will
  look there.
- Four tabs fit all three UI styles: `minimal` renders text-only labels (a
  fourth short label fits at `fontSize: 13`), `classic`/`edge` get the icon.
  No layout change needed in `TabsLayout` beyond the new `Tabs.Screen`.

The screen itself is a `ScrollView`: readout + graph card first, selectors,
then the calendar card.

## 3. Data layer — `src/core/dashboard/aggregate.ts`

Pure module (no `react-native`/`expo` imports), co-located
`aggregate.test.ts`. Imports only `TrackSummary` from `@core/models`.

### Time semantics (explicit)

- All bucketing uses **device-local time** via local `Date` methods
  (`getFullYear`/`getMonth`/`getDate`/`setDate`), never fixed
  `86_400_000`-ms arithmetic — buckets stay aligned to local midnight across
  DST transitions.
- **Weeks start Monday** (`getDay()` 1; Sunday belongs to the preceding
  Monday's week).
- A track belongs to the local calendar day/week of its `startedAt`.
  Re-bucketing after a timezone change is accepted behavior.

### Types

```ts
export type DashboardPeriod = '7d' | '3m' | '1y';

/** One graph point: a local day (7d) or a Monday-start local week (3m/1y). */
export interface ActivityBucket {
  /** Local midnight (day) or local Monday-midnight (week), epoch ms. */
  startMs: number;
  /** Exclusive end, epoch ms (next local midnight / next Monday-midnight). */
  endMs: number;
  distanceM: number;
  /** Sum of stats.movingTimeS; 0 when only untimed tracks fall in the bucket. */
  movingTimeS: number;
  /** Sum of stats.ascentM (D+). */
  ascentM: number;
  /** Contributing tracks, newest first. */
  trackIds: string[];
}

/** A calendar-month day that has at least one activity. */
export interface CalendarDayEntry {
  /** 1-based day of month. */
  day: number;
  /** Chronological by startedAt; category is the raw id (may be dangling). */
  tracks: { id: string; category?: string }[];
}
```

### Functions

```ts
/** Local midnight of the day containing t, epoch ms. */
export function startOfLocalDay(t: number): number;

/** Local Monday-midnight of the week containing t, epoch ms. */
export function startOfLocalWeek(t: number): number;

/** t shifted by whole local days (DST-safe, via Date#setDate). */
export function addLocalDays(t: number, days: number): number;

/**
 * Performed = anything except category 'navigation' (untimed imported routes
 * are plans, not activities — see §5). Uncategorized counts as performed.
 */
export function isPerformedActivity(track: Pick<TrackSummary, 'category'>): boolean;

/**
 * Whether a track passes the dashboard category filter.
 * null = all performed activities (isPerformedActivity);
 * 'navigation' = exactly the navigation trails;
 * any other id = strict equality with track.category.
 */
export function matchesCategoryFilter(
  track: Pick<TrackSummary, 'category'>,
  categoryId: string | null,
): boolean;

/**
 * The graph's buckets, oldest → newest, ALWAYS the full fixed count
 * (empty buckets have zero sums and empty trackIds):
 *   '7d' → 7 daily buckets ending with the local day containing `now`;
 *   '3m' → 13 weekly buckets ending with the current week;
 *   '1y' → 52 weekly buckets ending with the current week.
 */
export function aggregateBuckets(
  tracks: readonly TrackSummary[],
  period: DashboardPeriod,
  now: number,
  categoryId: string | null,
): ActivityBucket[];

/**
 * Per-day activity index for one local calendar month (month is 0-based),
 * filtered like aggregateBuckets. Only days with ≥1 match are returned,
 * ascending by day.
 */
export function calendarIndex(
  tracks: readonly TrackSummary[],
  year: number,
  month: number,
  categoryId: string | null,
): CalendarDayEntry[];
```

Label formatting (dates, distance, duration) is NOT in core — the feature
layer uses `formatDistance`/`formatDuration`/`formatElevation` from
`@lib/format` and `Date#toLocaleDateString` for the readout date.

## 4. UI composition — `src/features/dashboard/`

Files: `DashboardScreen.tsx`, `ActivityGraph.tsx`, `MonthCalendar.tsx`,
`DayActivitiesDialog.tsx`. All colors come from MD3 theme slots
(`useTheme()`) or `categoryColor()` — the screen must read correctly in all
three UI styles (classic/minimal/edge) × light/dark; category hexes are
already contrast-gated against both schemes.

### Accent color

`accent = categoryColor(selectedCategoryId, customCategories) ?? theme.colors.primary`.
The graph circles, aura, connecting line, and readout value texts all use it.

### Readout (above the graph)

Two lines, in the ElevationProfile readout idiom (`Text variant="bodySmall"`,
fixed `minHeight` so scrubbing never reflows the layout):

1. The selected bucket's date — day buckets: `Wed, Jul 22`; week buckets:
   `Jul 14 – 20` (`toLocaleDateString` with weekday/month/day options).
2. `12.4 km · 2h 05m · ↑ 640 m` — `formatDistance(distanceM)`,
   `formatDuration(movingTimeS)` (shown as `—` when `movingTimeS === 0`),
   `↑ formatElevation(ascentM)`. Values tinted `accent`; separators
   `onSurfaceVariant`.

Default selection: the newest bucket (today / current week).

### The period graph (`ActivityGraph`)

`react-native-svg`, following `ElevationProfile.tsx` idioms exactly: width
from `onLayout`, fixed height 150, `Svg` + `Circle`/`Line`, chart panel
`backgroundColor: theme.colors.surfaceVariant`, `borderRadius: 10`,
`overflow: 'hidden'`.

- One circle per `ActivityBucket`, x evenly spaced, y = `distanceM`
  normalized to the bucket max (zero-distance buckets sit on the baseline).
- **Unselected buckets: hollow circles** — `fill="none"`,
  `stroke={accent}`, strokeWidth 1.5.
- **Selected bucket: filled circle with a paler aura** — inner
  `Circle fill={accent}`, plus a second `Circle` behind it at 2.2× radius,
  `fill={accent}` `opacity={0.22}` (the aura; opacity on the same hex — no
  new hardcoded colors).
- Radii scale with density: 7d → r 5; 3m → r 3.5; 1y → r 2 (52 points across
  the plot width, Strava-style).
- A thin polyline connects the circle centers (`stroke={accent}`,
  `strokeOpacity={0.3}`, width 1) so sparse periods still read as a trend.
- **Scrubbing/selection**: the same `PanResponder` recipe as
  ElevationProfile (claim on start, `onPanResponderTerminationRequest: () =>
  false`, block the native responder so the parent ScrollView can't steal a
  drifting finger). Touch/drag snaps selection to the nearest bucket x;
  release KEEPS the selection (unlike ElevationProfile's transient scrub) —
  the readout always describes some bucket.
- Container `accessibilityLabel="Activity graph"`.

### Bottom selector row

Directly under the graph, one row, `justifyContent: 'space-between'`:

- **Bottom left — period selector**: Paper `SegmentedButtons` with values
  `7d` / `3m` / `1y`, labels `7d`, `3m`, `1y`, `density="small"`,
  accessibility labels `Past 7 days`, `Past 3 months`, `Past year`.
  Switching periods re-selects the newest bucket.
- **Bottom right — category selector**: a Paper `Menu` anchored on a
  `Chip` showing the current filter's icon + name (`All` by default,
  `accessibilityLabel="Filter by category"`). Menu items: **All**, then
  `allCategories(customCategories)` (built-ins first, customs after — the
  `navigation` built-in is listed and is the only way navigation trails
  appear, §5). Each item shows its `CategoryDefinition.icon` tinted with its
  `color`. The choice applies to BOTH the graph and the calendar.

### Month calendar (`MonthCalendar`)

Below the selector row, on a `surface` card:

- Header: `chevron-left` / month-year title (`July 2026`) / `chevron-right`
  (`IconButton`s, labels `Previous month` / `Next month`). Forward
  navigation stops at the current month; back navigation stops at the month
  of the oldest matching track.
- Grid: 7 columns, **Monday-first** (consistent with §3), single-letter
  weekday header row in `onSurfaceVariant`; day cells min 44 pt. Today gets
  a 1.5 pt ring in `theme.colors.outline`.
- A day with activities (from `calendarIndex`) renders, under the day
  number, the first activity's category icon (MaterialCommunityIcons,
  size 16) tinted by `categoryColor`; uncategorized/dangling categories
  render `circle-medium` in `onSurfaceVariant` (the existing "neutral
  fallback" rule from `findCategory`). **Two or more activities**: the icon
  plus a small count badge (Paper `Badge size={14}`) with the number.
- Cell accessibility label: `Jul 8: 1 activity` / `Jul 8: 3 activities`
  (empty days: `Jul 8: no activities`, not tappable).
- **Tap**: one activity → `router.push(`/trail3d/${id}`)` (the existing
  trail viewer route, `app/trail3d/[id].tsx`); multiple →
  `DayActivitiesDialog`.

### `DayActivitiesDialog`

Paper `Dialog` in a `Portal` (user-invoked from a settled screen — the #108
"no Portal on launch/error paths" rule does not apply), modeled on
`SetCategoryDialog.tsx`: title `Activities on Jul 8`, a `ScrollView` list of
`List.Item`s — category icon, track name, `formatDistance` ·
`formatDuration` description — each pushing `/trail3d/[id]` and dismissing.
Cancel action closes.

### State

Screen-local `useState` only (`period`, `categoryId`, `selectedBucketIndex`,
`visibleMonth`); nothing persisted. Aggregations run in `useMemo` keyed on
`tracks`, `period`, `categoryId` — at library scale (hundreds of tracks) a
full recompute per change is trivially cheap.

## 5. Edge cases

- **No activities at all** (no performed tracks): the graph/calendar cards
  are replaced by a centered empty state — `chart-line-variant` icon, "No
  activities yet", body "Record a trail from the Map tab and it will show up
  here." No dead selectors.
- **None in the selected period/filter**: the graph still renders its full
  fixed bucket count (all baseline hollow circles); readout line 2 reads
  `No activities` in `onSurfaceVariant`. The calendar renders normally.
- **Untimed navigation trails** (`category === 'navigation'`, imported GPX
  without timestamps; `startedAt` is the *import* time and `movingTimeS` is
  0): **excluded from "All"** — they are plans, not performed activities,
  and their import date would fabricate training volume. Selecting the
  "Navigation trail" category shows exactly them, bucketed by `startedAt`,
  with real distance/D+ and time rendered `—`.
- **Custom categories** aggregate and render like built-ins (icon
  `CUSTOM_CATEGORY_ICON`, their picked color). **Deleted/dangling category
  ids** (`findCategory` → null): the track counts under "All", renders the
  neutral `circle-medium` calendar glyph, and the dangling id is NOT offered
  in the category menu (only `allCategories()` output is).
- **Many activities on one day**: badge shows the true count (no cap needed
  at realistic scale); the picker dialog's list scrolls.
- **Period boundaries**: `'7d'` means today plus the 6 previous local
  calendar days (not a rolling 168 h); week periods end with the *current
  partial* week, so the newest bucket grows day by day. A track at 23:59
  Sunday belongs to the ending week; 00:00 Monday starts the next. DST-day
  buckets are 23/25 h long by construction (§3) and never drop or double a
  day.
- **Month calendar at year edges**: `calendarIndex(tracks, 2026, 0)` is
  January; chevrons cross year boundaries by decrementing/incrementing the
  (year, month) pair.

## 6. Testing

### Unit (`src/core/dashboard/aggregate.test.ts`)

Set `process.env.TZ = 'America/Toronto'` at the very top of the test file
(before any `Date` use) so local-time assertions are deterministic in CI.
Cases:

- `startOfLocalWeek`: a Wednesday → its Monday; a Sunday → the *previous*
  Monday; a Monday 00:00 → itself.
- `startOfLocalDay` / `addLocalDays` across the spring-forward and fall-back
  DST dates (2026-03-08, 2026-11-01): day buckets stay midnight-aligned.
- `aggregateBuckets` counts: exactly 7 / 13 / 52 buckets, oldest → newest,
  last bucket contains `now`.
- Summing: two tracks in one week sum `distanceM`/`movingTimeS`/`ascentM`
  and list both ids newest-first; empty buckets are all-zero with empty
  `trackIds`.
- Boundary placement: Sunday-23:59 vs Monday-00:00 tracks land in different
  weekly buckets; a track older than the window is excluded.
- Filtering: `null` excludes `'navigation'` but includes uncategorized and
  dangling-id tracks; `'navigation'` selects only navigation trails;
  a built-in/custom id matches strictly.
- `calendarIndex`: only days with matches, ascending; multi-activity day
  chronological; month/year edges (Dec→Jan); respects the category filter.
- `isPerformedActivity` / `matchesCategoryFilter` truth tables.

### E2E (`.maestro/dashboard.yaml`)

Runs after `category-record.yaml` in the suite — its fixture is that flow's
freshly recorded **Run** trail (recorded "today", so it is deterministically
in every period and on today's calendar cell). Same portability rules as the
other flows: per-platform `launchApp` permission blocks, accessibility-label
matching, `extendedWaitUntil` for slow software-GL emulators, and regex for
dynamic text. Outline:

1. `launchApp` (per-platform permissions) → `extendedWaitUntil: 'Map actions'`.
2. `tapOn: 'Dashboard(, tab.*)?'` → `assertVisible: 'Activity graph'`.
3. Readout shows real data: `assertVisible` text matching `.*km.*` (the
   default newest bucket contains today's recorded trail).
4. `tapOn: 'Past 3 months'` → `assertVisible: 'Activity graph'` (period
   switch doesn't blank the readout: assert `.*km.*` again).
5. `tapOn: 'Filter by category'` → `tapOn: 'Run'` → readout still matches
   `.*km.*` (the fixture is a Run).
6. Calendar: `assertVisible` matching `.* 1 activity` (today's cell) →
   `tapOn` it → `extendedWaitUntil` the trail viewer is visible (the trail3d
   screen's title/back affordance) → `back`.
7. `tapOn: 'Filter by category'` → `tapOn: 'Ski'` → `assertVisible: 'No
   activities'` (a filter with no matches shows the empty readout, proving
   the filter is real).

Both platforms (Android + iOS) as with every existing flow; all new
interactive elements carry the accessibility labels specified in §4.

## 7. Release

- **JS-only — confirmed no new native dependencies**: `react-native-svg`,
  `react-native-paper`, `expo-router`, and `zustand` are all already in the
  app; core is pure TS. No config-plugin, manifest, or pod changes.
- Therefore the feature is **OTA-compatible with runtime 1.4.0** (the
  current store build, vc49; `runtimeVersion` follows `appVersion` in
  `app.config.ts`). Ship order:
  1. Implement + fully test (unit, `npm run check`, both-platform Maestro
     including dark mode per the usual checklist).
  2. Publish as an EAS Update to the production branch for runtime 1.4.0 —
     users get the dashboard without a store release.
  3. The user's versioning intent: **the dashboard defines 1.5.0.** When the
     feature is complete, bump `version` to `'1.5.0'` and `versionCode` to
     `50` (vc50) in `app.config.ts` and cut the next store build from that —
     new installs then embed the feature and start the 1.5.0 runtime
     lineage. Follow `docs/DEPLOYMENT.md`; per the release-gotchas notes,
     verify what devices on each live runtime actually receive.

## 8. Out of scope

- Heart-rate zones / training load / fitness-freshness curves (HR stays a
  per-trail curve in `ElevationProfile`).
- Social features: profiles of others, following, feeds, kudos, segments,
  leaderboards.
- Awards, badges, streaks, goals, personal records.
- Any Strava *sync* of dashboard data (the existing `src/core/strava` upload
  path is untouched).
- Exporting/sharing the dashboard as an image.
- Persisting dashboard UI state (period/category/month) across launches.
- New chart libraries — `react-native-svg` only.
